# Pyrite64 → Desktop + Mobile Export Plan

Goal: Extend the Pyrite64 engine to export games for **Windows, Linux, macOS, iOS, and Android** using the **SDL3 GPU API** as the unified rendering backend. The N64 export target remains intact.

## Strategy

Keep the editor and the N64 engine as-is. Create a new **desktop/mobile runtime** that:

1. Reuses the portable parts of the N64 engine (collision, scene graph, events, components)
2. Reuses the editor's existing SDL3 GPU rendering infrastructure
3. Adds a new platform abstraction layer for window/input/audio
4. Adds a new build target in the editor that packages games for desktop/mobile

SDL3 GPU API covers all targets: Vulkan (Linux/Android), Metal (macOS/iOS), DirectX 12 (Windows).

## Phase 1: Project Restructuring

### 1.1 Create new runtime directory

```
runtime/                      # NEW: cross-platform game runtime
├── CMakeLists.txt
├── src/
│   ├── main.cpp              # Entry point (SDL_main)
│   ├── platform/             # Platform abstraction layer
│   │   ├── window.cpp        # SDL3 window + GPU device
│   │   ├── input.cpp         # Keyboard/gamepad/touch
│   │   ├── audio.cpp         # SDL3 audio
│   │   └── filesystem.cpp    # Asset loading from disk/bundle
│   ├── engine/               # Ported engine (mirrors n64/engine/)
│   │   ├── scene/            # Scene, objects, components
│   │   ├── collision/        # Copied verbatim from n64/engine
│   │   ├── renderer/         # NEW: SDL3 GPU renderer
│   │   ├── audio/            # NEW: SDL3-based audio manager
│   │   ├── script/           # Script runtime (adapted)
│   │   └── lib/              # Math, types, event system
│   └── components/           # Runtime component implementations
└── shaders/                  # GLSL source → compiled to SPIR-V
```

### 1.2 Update top-level `CMakeLists.txt`

Add new targets alongside `pyrite64` (editor):

- `pyrite64-runtime` — static library with the engine
- `pyrite64-game` — game executable that links the runtime + user scene data

New CMake presets needed:

- `macos-debug` / `macos-release`
- `ios-debug` / `ios-release` (cross-compile)
- `android-debug` / `android-release` (via Android NDK)

Mobile builds require platform-specific packaging (Xcode project for iOS, Gradle for Android) — likely generated by the editor at export time.

## Phase 3: Build the SDL3 GPU Runtime Renderer

Reuse the editor's rendering code from `src/renderer/`. These files are already generic (no N64 emulation specifics at the infrastructure layer):

### 3.1 Reuse from editor (copy or share via common lib)

- `src/renderer/pipeline.h/cpp` — SDL3 GPU pipeline wrapper
- `src/renderer/framebuffer.h/cpp` — render targets
- `src/renderer/texture.h/cpp` — texture loading
- `src/renderer/vertBuffer.h/cpp` — vertex buffers
- `src/renderer/shader.h/cpp` — SPIR-V shader loader
- `src/renderer/mesh.h/cpp` — mesh container
- `src/renderer/scene.h/cpp` — scene rendering with callback passes

**Recommendation:** Extract these into a shared library `vendored_shared/` or `common/renderer/` so both the editor and the runtime link against the same code. This avoids code duplication.

### 3.2 New runtime renderer files

- `runtime/src/engine/renderer/renderer.cpp` — main render loop, manages pipelines and passes
- `runtime/src/engine/renderer/material.cpp` — **new material system** (replace N64 color combiner)
- `runtime/src/engine/renderer/camera.cpp` — view/projection matrices via GLM
- `runtime/src/engine/renderer/lighting.cpp` — directional + point lights as uniforms

### 3.3 New shaders

Located in `runtime/shaders/`:

- `standard.vert.glsl` / `standard.frag.glsl` — replaces `n64.*.glsl`, does standard lit rendering (Phong or PBR)
- `unlit.vert.glsl` / `unlit.frag.glsl` — unlit materials
- `sprites.vert.glsl` / `sprites.frag.glsl` — can reuse editor's
- `lines.vert.glsl` / `lines.frag.glsl` — can reuse editor's

Build pipeline: `shaders/build.sh` compiles GLSL → SPIR-V with `glslc`, outputs to `runtime/data/shaders/`. Same pattern as `src/shader/build.sh`.

### 3.4 Drop (or reimplement later)

- **HDR Bloom pipeline** — RSP microcode, has no direct equivalent. Either drop for v1 or reimplement as a GPU post-process pass (fragment shaders: bright-pass → blur → composite). Desktop GPUs handle this trivially.
- **BigTex pipeline** — solves N64's 64KB TMEM limit. Not needed on desktop/mobile — just use standard texturing with any resolution.

## Phase 4: Platform Abstraction Layer

### 4.1 Window + GPU device (`runtime/src/platform/window.cpp`)

```cpp
// Uses existing SDL3 code from src/main.cpp as reference
SDL_Window* window = SDL_CreateWindow(...);
SDL_GPUDevice* gpu = SDL_CreateGPUDevice(SDL_GPU_SHADERFORMAT_SPIRV, true, nullptr);
SDL_ClaimWindowForGPUDevice(gpu, window);
```

Platform-specific flags:

- Windows/Linux/macOS: standard desktop flags
- iOS/Android: fullscreen, handle orientation, safe areas via `SDL_GetWindowSafeArea`

### 4.2 Input (`runtime/src/platform/input.cpp`)

Unified input abstraction over:

- Keyboard (`SDL_EVENT_KEY_*`)
- Gamepad (`SDL_EVENT_GAMEPAD_*`) — maps to N64 controller layout for compatibility with existing game code
- Touch (`SDL_EVENT_FINGER_*`) — for mobile; maps to virtual gamepad or direct touch handlers

Expose the same `joypad_*` style API that the existing engine code uses, so ported components don't need to change.

### 4.3 Audio (`runtime/src/platform/audio.cpp` + `runtime/src/engine/audio/audioManager.cpp`)

Replace `n64/engine/src/audio/audioManager.cpp` logic:

- Use SDL3's audio device + audio streams (`SDL_OpenAudioDeviceStream`)
- For WAV: use `SDL_LoadWAV`
- For XM tracker files: vendor **libxmp** or **libopenmpt** (both cross-platform, MIT/BSD)
- Keep the existing slot manager, handle UUID system, volume/speed controls — only the decoder backend changes

### 4.4 Filesystem (`runtime/src/platform/filesystem.cpp`)

- Desktop: read from `./assets/` next to executable
- iOS: read from app bundle via `SDL_GetBasePath()`
- Android: read from APK assets via SDL3's Android asset support (`SDL_IOFromFile` handles this automatically)

## Phase 5: Build System Extensions

### 5.1 Editor changes (`src/build/`)

Add a new export target type:

- `src/build/projectBuilder.h` — add `enum class Target { N64, Desktop, iOS, Android }`
- `src/build/desktopBuilder.cpp` — **NEW**: packages game for desktop/mobile
  - Copies runtime executable
  - Serializes scenes to binary (reuse `sceneBuilder.cpp` — format is already platform-independent)
  - Converts assets:
    - Models: keep T3DM for now (simplest), or convert to GLTF for mobile
    - Textures: convert to platform-appropriate formats (KTX2 for compressed textures on mobile)
    - Audio: keep WAV/XM
  - Bundles shaders (compiled SPIR-V)
  - Outputs:
    - Windows: `.exe` + DLLs + `assets/` folder
    - Linux: ELF binary + `.so` files + `assets/`
    - macOS: `.app` bundle
    - iOS: Xcode project to build via `xcodebuild`
    - Android: Gradle project to build via `./gradlew assembleRelease`

### 5.2 Editor UI

- Add "Build Target" selector to project settings
- Add "Export for Desktop / iOS / Android" menu items
- Show platform-specific options (code signing for iOS/macOS, keystore for Android)

## Phase 6: Scripting & User Code

The existing `compCode` (user C++ scripts) currently compiles to MIPS via libdragon's toolchain. For desktop/mobile:

### 6.1 Option A: Native compilation per platform (recommended for v1)

- Desktop: compile user scripts with host GCC/Clang during export
- iOS: compile with Xcode clang during Xcode project build
- Android: compile with NDK clang during Gradle build

Editor's `scriptBuilder.cpp` needs a platform-aware compilation step.

### 6.2 Option B: Interpreted scripting (future)

Consider adding a scripting language (Lua via sol2, or WASM) for iterate-without-recompile. Not required for v1.

### 6.3 Node graph scripting

- Replace libdragon coroutines with **C++20 coroutines** (`co_await`, `co_yield`)
- The graph data format stays identical
- Only the runtime execution loop changes (~100 lines)

## Phase 7: Platform-Specific Considerations

### Windows

- Use MSYS2 UCRT64 (matches existing CI) or MSVC
- Static link SDL3 to avoid DLL hell
- Ship `SDL3.dll` if dynamic

### Linux

- AppImage or Flatpak for distribution
- Same CMake preset already exists for the editor

### macOS

- `.app` bundle with `Info.plist`
- Code signing + notarization (required for distribution outside Mac App Store)
- Metal backend via SDL3 GPU is automatic

### iOS

- Minimum iOS 13+ (for Metal + modern Swift runtime)
- Touch input required; no keyboard/gamepad guaranteed
- App Store requires specific icon sizes, launch screens, privacy manifest
- TestFlight for beta distribution
- SDL3 has an iOS template project — use it as starting point

### Android

- Minimum API 26+ (Android 8.0) for Vulkan 1.1
- Touch input + optional gamepad
- Google Play requires AAB format and signed with keystore
- Permissions in `AndroidManifest.xml` (network, storage as needed)
- SDL3 has an Android template project — use it as starting point

### Mobile UX considerations

- Virtual on-screen joystick for touch-only games (add as SDL3 widget or render manually)
- Safe area insets (notches, home indicators)
- Different screen aspect ratios — needs flexible UI scaling
- Pause/resume lifecycle — `SDL_EVENT_WILL_ENTER_BACKGROUND` / `_DID_ENTER_FOREGROUND`

## Open Questions Before Starting

1. **Shader strategy:** Port N64 color combiner look, or embrace modern PBR? (Affects shader complexity and visual style)
2. **Asset conversion:** Keep T3DM format on desktop, or convert to GLTF at export? (T3DM is simpler; GLTF is more portable)
3. **Mobile scope:** Ship v1 as desktop-only and add mobile after, or go for all platforms at once? (Desktop-first is faster to a working demo)
4. **HDR Bloom:** Drop entirely, or implement GPU version? (GPU version is ~200 lines of shader + 1 post-process pass)
5. **Script compilation:** Is on-device compilation acceptable on mobile, or do user scripts need to be precompiled during export? (Mobile app stores generally forbid shipping compilers; precompile at export is safer)
